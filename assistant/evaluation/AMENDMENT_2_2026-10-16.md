# Amendment 2 to protocol v2 (16 October 2026, Canberra): written before the sealed set was built

**Measurement.** A dry run of `build_sealed.py` into scratch (output not used) showed that 7K9D and 6DCB are among the
66 stress-pair targets in `work/sp_in`. Both are development targets in protocol v2 §3:
- 7K9D is the bundled example, used in the development pilot (task d1);
- 6DCB is the first-use and regression case.

The builder's development set held only the six stress-cohort development targets, so it placed 7K9D (A5) and 6DCB
(A4) into the evaluation pool.

**Why the frozen text was wrong.** Protocol v2 §3 says that development targets are "never for sealed tasks". It also
says that the evaluation targets are "the 66 stress-pair targets minus the six development targets, which leaves 60".
These conflict. I wrote the count without checking whether 7K9D and 6DCB are in that table. That was my error.

**Replacement.**
- The rule takes precedence. The evaluation pool is the 66 stress-pair targets minus all eight development targets
  (1VTM, 24BR, 2JEA, 2Q66, 2QQP, 2XGJ, 7K9D, 6DCB), which leaves **58**.
- Of these, targets whose unmodified predictions the reference workflow cannot import are ineligible (Amendment 1,
  A1.3). In the dry run these were 4C9D and 4I67.

**Unchanged.** Seeds, the assignment procedure, templates, keys rules, scoring and everything else.

The dry-run directory is not the sealed set; it is kept under `scratch_agent/` as a non-authoritative record. Only the
assignment and structural counts were printed; no answer of any arm existed.
