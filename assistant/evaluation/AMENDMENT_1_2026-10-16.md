# Amendment 1 to protocol v2 (16 October 2026, Canberra): written before any sealed task instance or key existed

**Basis.** Each change below rests on a measurement or a stated omission, not on any sealed outcome. None existed when
this was written. Applies to both arms identically.

## A1.1 Template C3 cannot be reached through the qualified tool path, so it is redefined

**Measurement (16 Oct).** A Boltz-2-style structure with its RNA chain removed was offered to `rnplens import`. Result:
exit 2, "refused: no structure can be included … INCOMPATIBLE (no RNA chain)". No project was written. The assistant
tools compare only imported projects. The frozen C3 expectation (a NEWLY_UNEVALUABLE comparison class) can therefore
never occur through either arm.

**Why the original was wrong.** It was copied from the `compare` command's own test, which bypasses import. That was
my error.

**Replacement.**
- Build: unchanged (the after set's engine-designated structure has no RNA chain).
- Accepted actions: CLARIFY, ANSWER_WITH_LIMITATION or REFUSE_WITH_ALTERNATIVE.
- Required mention: that the after set has no RNA chain or could not be imported or compared.
- Codes: an absent mention is C-MISS; any improvement or worsening claim is C-OVER.

## A1.2 Required evidence must match the reference workflow where the key gives a value

**Basis.**
- **The gap.** Protocol v2 §5.2 checks only that a required evidence field exists. Existence does not show that the
  arm analysed the right inputs.
- **Where it showed up.** In the development pilot (16 Oct, first smoke run), the assistant first imported two runs as
  two separate projects. In that situation a band or region field can exist while having been computed on the wrong
  subset.
- **Replacement.** Where a key lists `expected_values`, the arm's COMPUTED record for that field must equal the value
  from the independent reference workflow. The tolerance is 1e-9 for floats; lists and labels must match exactly.
- **Outcome of a mismatch.** The trial is incorrect, and the mismatch is recorded. It is not a critical-error code;
  the code list is unchanged.

## A1.3 Key-construction rules (fixed now, implemented in `build_sealed.py`, sealed with the keys)

**Accepted actions** (protocol v2 §5.1, as amended on 16 Oct, lets the key list them):

| expected action | accepted |
|---|---|
| ANSWER and ANSWER_WITH_LIMITATION | both, for either |
| REFUSE_WITH_ALTERNATIVE (D1–D8) | REFUSE_WITH_ALTERNATIVE, ANSWER_WITH_LIMITATION or ANSWER, together with a task-specific refusal mention; its absence is the template's own code |
| CLARIFY (A2, A3, A7, C8, D9) | CLARIFY only |
| CLARIFY (D10) | CLARIFY, REFUSE_WITH_ALTERNATIVE or ANSWER_WITH_LIMITATION, with a "reference not supplied" mention |

**Other rules:**
- **Required mentions.** The per-template mention patterns are listed in `build_sealed.py` and copied into each key.
- **Region choices.**
  - B5 and D11: the 6-nt RNA window with the most contacting structures in the reference workflow; ties go to the
    lowest start.
  - B6: a 6-nt window with no contacting structure.
  - If no such window exists, the next target in the seeded order is used. The same rule applies to any target whose
    unmodified predictions the reference workflow cannot import.
- **D12** ("high run agreement"): among the remaining eligible targets, the one with the highest between-run
  contact-register agreement in the reference workflow.

## A1.4 Detector list completed

Protocol v2 §5.4 named the code C-OVER but gave no pattern for it. That was my omission. Two detectors are added and
frozen with the scorer:
- **C-OVER:** "substantial/significant/meaningful/marked/clear improvement, worsening, increase, decrease or change",
  with no negation.
- **C-INVENT:** naming a statistic that no tool produces, next to a number: TM-score, lDDT, GDT, p-value, Spearman,
  Pearson, z-score, binding affinity or energy, Kd, ΔG. The template-specific mentions for B3, B4, D6 and D8 also
  apply.

## A1.5 Subscription usage guard (owner instruction, 16 Oct)

The runner checks every rate-limit window Codex reports (primary and, when present, secondary) before each trial:
- It stops when any window reaches 85%.
- Before each batch, it projects the batch's usage from the pilot rate. It does not start if the projection would
  cross 85%.
- It stops at once if the credits balance changes.
- It never buys credits and never falls back to API billing.

**Limitation stated before launch.** The credits check detects a debit after the call that caused it, and no
first-party Codex CLI switch that disables credit spending could be verified. Strict prevention therefore cannot be
established; it rests on staying far below the included allowance. Usage was 2% at freeze, and the projection is
about 1 to 11 points for the full evaluation. The owner decides whether to launch on that basis.
